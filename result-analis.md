# Анализ проекта FileSignature (студенческая работа)

Оценка выполнена только чтением исходного кода (синтаксический анализ). Код не собирался и не запускался. Утверждения о гонках и зависаниях нужно подтвердить запуском.

## Итоговая оценка: 5 из 10

Базовая идея верная: файл читается потоком, блоки хешируются SHA256 в отдельных `Thread`, ошибки выводятся с текстом и StackTrace. Но в коде есть гонки, из-за которых результат может быть неполным или программа может зависнуть. Есть busy-wait, который загружает все ядра. Очередь не ограничена, что противоречит требованию работать с файлами больше ОЗУ.

## Критические ошибки

1. **Последний блок может быть потерян.** В `WorkerThreadManager.cs:57` элемент извлекается из очереди. Затем в `:63–65` цикл прерывается, если `_needToStop` уже выставлен и очередь пуста. Извлечённый элемент никому не передаётся и не обрабатывается. Результат недетерминированный: зависит от того, успел ли диспетчер извлечь последний блок до `FinishAndStop()`.

2. **Гонка при запуске и остановке потоков.** `_workerThreads` создаётся внутри потока `Process()` (`:49`), но `StopWorking()` (`:93`) и `Join()` (`:103`) обращаются к нему из главного потока. Если файл пустой или очень маленький, `Join()` в `finally` (`Program.cs:67`) может выполниться раньше создания массива, и будет `NullReferenceException`. Флаги `_inProgress` (`WorkerThreadManager.cs:48`, `WorkerThread.cs:59`) выставляются внутри потоков. Если сигнал остановки пришёл раньше, он теряется, поток крутится вечно, и `Join()` зависает.

3. **Ошибка в рабочем потоке не перехватывается.** `WorkerThread.ThreadProc` (`WorkerThread.cs:55–77`) ловит только `ThreadAbortException`. В .NET Core `Thread.Abort` не работает, так что этот `catch` фактически мёртв. Любое исключение из `Calculate()` выходит за пределы потока, процесс падает, а `catch` в `Program.Main` не срабатывает. Требование про вывод текста и StackTrace для ошибок в потоках не выполнено.

4. **Литерал `/n` вместо `\n`** (`SHA256Block.cs:50`). Каждая строка вывода заканчивается `/n`.

5. **Busy-wait.** В `WorkerThread.cs:60–68` каждый рабочий поток крутит цикл без паузы, даже когда работы нет. В `WorkerThreadManager.cs:61–79` диспетчер тоже крутит цикл, пока все воркеры заняты. На 6 ядрах получается 7 потоков по 100% CPU, и на хеширование остаётся меньше мощности, чем могло бы быть. Возможно, это объясняет, почему в таблице из README 2 потока работают дольше, чем ожидается, и почему время почти не зависит от размера блока. Это предположение, проверить его можно профилировщиком.

6. **Неограниченная очередь.** Все блоки, которые читатель опережает, хранятся в памяти. Для файла в десятки гигабайт и медленной обработки это исчерпание памяти, то есть ровно то, что задание запрещает.

## Качество кода

**Положительное:** разделение на классы и интерфейсы, `using` в `try`, `ProcessorCount` по умолчанию, `Utility` с рекурсивным обходом `InnerException`, отдельный `Stopwatch`, измерения в README.

**Замечания:**

- **Переусложнение.** `IWorkItem`, `WorkItem`, `WorkItemCreator` и `WorkerThreadManager` описывают одну и ту же очередь задач несколькими слоями. `WorkItemCreator` хранит состояние между двумя вызовами (`SetDataBlock`, `CreateWorkItem`), а параметр `state` нигде не используется.
- **Смешение ответственностей.** `SHA256Block` и хеширует, и хранит данные, и форматирует вывод. Лучше разделить вычисление и печать.
- **Неиспользуемые поля и `using`.** В `BlockBuilder`: `_currentPositionInFile` не читается, `_fileSize` только присваивается, `_bytesRead` накапливается без использования. Лишние `using`: `Utility.cs:2–3`, `IBlock.cs:1`, `SHA256Block.cs:3`, `IWorkItem.cs:2–3`, `BlockBuilder.cs:2,4`.
- **Пустое исключение.** `SHA256Block.cs:33`: `throw new Exception($"", ex)` без сообщения. Ветка `else` в `:37–40` недостижима, потому что `_data` всегда не null.
- **Короткое чтение.** `BlockBuilder.cs:38` делает один `Read`. Для `FileStream` это обычно полный блок, но контракт `Stream` этого не гарантирует. Короткое чтение посреди файла сдвинет границы блоков. Нужен цикл, пока буфер не заполнен или `Read` не вернул 0.
- **Выделение памяти на каждый блок.** `BlockBuilder.cs:36` создаёт новый `byte[]` для каждого блока. Блоки по 512 КБ и больше попадают в Large Object Heap, и для большого файла это много сборок мусора второго поколения. Буферы стоит переиспользовать.
- **`SHA256.Create()` на каждый блок** (`SHA256Block.cs:25`). Хешер можно создать один раз на поток.
- **Разбор аргументов.** `args[0]` и `args[1]` читаются без проверки длины (`Program.cs:17, 26`). Без аргументов будет `IndexOutOfRangeException` с непонятным текстом. Если третий аргумент не парсится, программа тихо берёт число потоков по умолчанию (`:31–39`), хотя должна сообщить об ошибке. `new NumberFormatInfo()` здесь не нужен, достаточно `int.TryParse(s, out x)`.
- **Код возврата.** `Main` возвращает `void`, поэтому при ошибке процесс завершается с кодом 0. Лучше возвращать `int`.
- **Порядок вывода.** Строки пишутся в порядке завершения потоков. Для сигнатуры, которую потом сравнивают, порядок важен. Либо выводить по порядку номеров, либо явно написать, что порядок не гарантирован.
- **Мелочи.** Пространство имён `Veeam.FileSignature` в папке `Blocks/` не совпадает с папкой. Устаревшие комментарии (`//TODO: Do smth with abort`, `//dequeue some data`). `IBlock.cs` содержит `using System.IO`, который не используется. Свойство `EoF` лучше назвать `Eof` или `IsEndOfFile`.
- **Git.** В репозитории отслеживается `.vs/` (в `git status` виден изменённый `.dtbcache.v2`). Эти файлы надо убрать из индекса и добавить в `.gitignore`.
- **Версия фреймворка.** `netcoreapp3.1` (`Veeam.FileSignature.csproj:5`) давно не поддерживается. Для учебной работы это не критично, но при обновлении проекта стоит перейти на `net8.0`.

## Рекомендации студенту

### Приоритет 1: корректность

- Замените самописную очередь и busy-wait на `BlockingCollection<IBlock>` с ограниченной ёмкостью. Это стандартный шаблон «производитель–потребитель», он входит в `System.Collections.Concurrent` и не запрещён заданием. Ограниченная ёмкость решает проблему памяти, а блокирующее ожидание убирает busy-wait.

  ```csharp
  var queue = new BlockingCollection<IBlock>(boundedCapacity: threadCount * 2);

  var workers = new Thread[threadCount];
  for (int i = 0; i < threadCount; i++)
  {
      workers[i] = new Thread(() =>
      {
          foreach (var block in queue.GetConsumingEnumerable())
          {
              block.Calculate();
              Console.WriteLine(block);
          }
      });
      workers[i].Start();
  }

  using (var reader = new BlockBuilder(fileInfo, blockByteSize))
  {
      IBlock block;
      while ((block = reader.BuildNextBlock()) != null)
      {
          queue.Add(block); // блокируется, когда очередь полна
      }
  }

  queue.CompleteAdding();
  foreach (var worker in workers)
  {
      worker.Join();
  }
  ```

  В таком варианте `CompleteAdding()` и `Join()` дожидаются обработки всех блоков, так что последний блок не теряется. В тело потока всё ещё нужно добавить `try/catch`: исключение надо сохранить, поднять в основном потоке после `Join()` и остановить остальных потребителей. Иначе ошибка в одном потоке снова уронит процесс.

- Уберите самописные флаги `_inProgress`, `_needToStop` и `Status`. Сигнал завершения дают сама очередь и `Join()`.
- Ловите исключения в каждом рабочем потоке и передавайте их в основной поток.
- Исправьте `\n` в `SHA256Block.ToString`.
- В `BlockBuilder` сделайте цикл чтения, пока буфер не заполнен или `Read` не вернул 0.

### Приоритет 2: производительность

- Переиспользуйте буферы: пул из `threadCount * 2` массивов, которые возвращаются в пул после хеширования.

- Измерьте, сколько времени занимает чтение с диска и сколько хеширование, прежде чем «ускорять» одно из них.

### Приоритет 3: структура и стиль

- Уберите `IWorkItem`, `WorkItem`, `WorkItemCreator`. Рабочий поток может просто брать `IBlock` из очереди.
- Разделите вычисление хеша и форматирование вывода.
- Удалите неиспользуемые поля и `using`.
- Проверяйте количество аргументов и печатайте короткую справку (usage) при неверном вызове. Если число потоков не парсится, сообщайте об ошибке, а не подставляйте значение по умолчанию.
- Верните из `Main` код возврата: 0 при успехе, ненулевой при ошибке.
